## 当前异步回执为何覆盖草稿

当前正式 `reagents_page.cpp:916–922`原来直接发 `requestRemoveBarcode`，没有确认。后台 `ReagentStore::removeBarcode`在 `reagent_store.cpp:618–621`转到 `remove:585–607`；原资料模式核 `originalMayEdit`后调用Editor删除，并走 `original_reagent_store.cpp::finishOriginal:615–620`。成功顺序是先 `succeeded("删除条码")`，再 `loadOriginal`，读取成功发 `loaded(snapshot)`。本地旧资料模式的 `finish:372–390`同样在提交成功后先发succeeded再load。

Page的公共succeeded槽先统一 `dirty_=false`，公共loaded槽再采用快照、清忙并发 `snapshotChanged`，最后才清 `pendingSavedOperation_`并报操作结束。资料窗原snapshotChanged槽看到dirty已被清除，就执行 `populate()` / `display()`，把尚未保存的输入换成库中旧值。

| 场景 | 候选处理和代码位置 |
| --- | --- |
| 点击删除 | `btnDelCode`回调`:925–956`恢复原文字的询问框。确认前记录试剂ID、条码ID/文字和资料根；确认后重新检查窗口仍在、原选择仍对应、当前权限/忙状态和已存列表。确认框处理事件期间发生变化则不换目标提交。现有canEdit条件和后台权限校验未放宽。 |
| 否、取消、关闭询问框、无所选条码 | 不改变草稿或列表，不设busy，不发requestRemoveBarcode。无所选条码时仍按原先询问、确认后无动作的顺序处理。 |
| 后台删除成功、重读成功 | 公共succeeded槽`:293–295`只对“删除条码”保留原dirty值。资料窗snapshotChanged在`:960–981`识别该已提交待读回操作，执行局部 `refreshCodes(true)`，有条码时选第0项、无条码时留空；直接返回，不调用populate/display，不关闭父窗。 |
| 草稿后来继续保存 | 条码和试剂资料同在Information库，删除会改变库指纹。删除前只在当前草稿版本等于已读记录版本时保留独立的已存整行。读回后只有同资料根、同ID、当前草稿版本仍对应，且整行字段名、类型、NULL状态和值完全相同，才更新当前记录的版本凭据（`:964–976`）。不替换任何输入、原始字段或脏标记。整行变化/缺行/旧版本不匹配时不更新凭据，原过期保存保护继续拒绝。 |
| 删除失败 | Store直接发error，不走succeeded。公共错误槽清busy并显示错误，dirty和输入不变，条码列表没有冒充删除成功。 |
| 已提交但重读失败 | 仍按现有公共错误槽显示“数据库已保存，但重新读取失败”，不报告操作全部成功。没有新快照时保留界面旧列表、输入和dirty，不猜删除结果、不伪造读回或回滚；列表需后续实际重读核实。 |
| 无关快照/显式保存取消 | 不匹配“删除条码”时仍走原dirty/busy守卫和原populate/display；显式资料保存、取消、关闭仍沿原逻辑。本片不扩展这些操作的规则。 |

条码列表构造被提取为局部 `refreshCodes`（`:783–792`）；普通display调用false保留原初次选择行为，只有删除读回调用true恢复原删除后选第0项。新增的已存整行副本只在GUI持有一份，绑定资料窗寿命，不跨线程携带控件或SQL连接，不增加线程/计时器/查询。使用 `pendingSavedOperation_`依赖的是同一个Store先succeeded再loaded、loaded发snapshotChanged后才清该字段的既有顺序；没有把任意外来快照当删除回执。

独立保存删除前的已存行还避免拿 `current.originalValues`中可能包含的先前保存失败输入当作原库依据。即使用户此前在保存时改变了针/清洗选项后因阈值错误未保存，这些草稿也不会被删除回执覆盖或误当作已存事实。是否在RK复现通过仍待验。
