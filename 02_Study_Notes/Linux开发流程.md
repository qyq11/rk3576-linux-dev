RK3576 嵌入式 Linux 系统定制与部署流程：
$$
从获取源码\rightarrow编译固件\rightarrow修改内核、配置系统服务\rightarrow将系统烧录到开发板并验证
$$

## 一、这些任务之间的关系

RK3576 Linux 开发主流程

1. 获取 SDK 与开发资料

获得源码、工具链、设备树、编译脚本和官方固件

2. 修改系统源码与配置

内核、设备树、实时补丁、SSH、Samba、网络配置

3. 编译并打包镜像

生成内核、根文件系统和可烧录的固件文件

4. 烧录 RK3576 开发板

通过 USB 下载模式或其他板卡支持的方式写入存储

5. 启动、串口观察与功能验证

TTL 日志、固定 IP、SSH、Samba、实时性测试

6. 发现问题后重新修改

形成“修改 → 编译 → 烧录 → 验证”的开发闭环

其中，SSH、Samba、固定 IP 和 TTL 日志是最终系统需要具备的功能要求；实时补丁是内核层面的定制要求；SDK、编译、镜像和烧录则是实现这些要求所必须掌握的开发手段。

## 二、关键概念与它们的区别

RK3576 与 Linux

RK3576 是 Rockchip 的 SoC 芯片，Linux 是运行在芯片上的操作系统。开发板还包含 DDR、eMMC、网络接口、电源及外围电路，因此相同芯片的不同开发板不能随意混用固件。

SDK（Software Development Kit）

开发套件，通常包含 U-Boot、Linux 内核、设备树、根文件系统构建工具、交叉编译工具链和打包脚本。它是你修改和重新生成系统的基础，不只是一个安装包。

IMG（镜像文件）

一种二进制文件的扩展名。在 RK3576 开发中，它可能是完整固件，也可能只是 boot、rootfs 等分区镜像。不能仅凭 .img 后缀判断内容，需要看 SDK 的打包说明。

内核（Kernel）

Linux 的核心，负责进程调度、内存、驱动、中断和硬件管理。修改内核代码或应用 PREEMPT_RT 实时补丁，属于内核层面的开发。

根文件系统（Rootfs）

Linux 启动后看到的 /bin、/etc、/usr 等目录。SSH 服务、Samba 服务、网络配置和用户账号通常主要在根文件系统中，而不是直接写进内核。

设备树（Device Tree）

描述板级硬件连接和启用状态，例如 UART 使用哪些引脚、以太网 PHY 如何连接、某个外设是否启用。驱动是“怎么操作硬件”，设备树是“这块板上硬件怎么连接”。

### 系统启动时，各部分如何配合？

BootROM → Loader / U-Boot

加载 Linux Kernel + Device Tree

挂载 Rootfs，启动 init / systemd

启动网络、SSH、Samba 等服务

这个顺序解释了为什么必须先解决启动和串口日志，再去排查 SSH 或 Samba：如果内核没有正常启动，后面的服务根本不会运行。

## 三、mentor 的每项要求具体意味着什么

### 1. 获取 SDK、IMG、刷写系统及修改文件

你需要学会区分两种工作：

直接使用官方固件

下载现成 IMG → 使用烧录工具 → 开发板启动。适合确认硬件、启动方式和网络是否正常。

使用 SDK 自己构建

下载源码 → 修改配置或代码 → 编译 → 打包 IMG → 烧录。适合完成导师要求的系统定制。

实际开发中应当先用官方固件成功启动，再开始自己编译。这样如果自编译固件无法启动，你可以区分是硬件问题还是软件构建问题。

需要掌握的文件修改方式主要有三类：修改内核 C 源码、修改设备树 DTS/DTSI、修改根文件系统中的配置文件与服务脚本。它们作用不同，不要把所有功能都理解成“修改内核”。

### 2. 编译镜像与内核实时补丁

实时补丁（PREEMPT_RT）

普通 Linux 主要追求整体吞吐量和公平调度；实时 Linux 更关注高优先级任务在规定时间内得到响应的确定性。PREEMPT_RT 通过改进内核抢占、锁和中断处理机制，减少最坏情况下的调度延迟。

普通内核

任务可能因为内核不可抢占区段、中断或锁等待而出现较大延迟。

PREEMPT_RT 内核

使更多内核路径可抢占，并将大量中断处理线程化，从而降低高优先级实时任务的响应延迟。

重要：实时补丁不是随便下载一个 patch 文件就能打上去。 必须确认当前 RK3576 SDK 的内核版本、Rockchip 厂商补丁、PREEMPT_RT 对应版本以及是否已经集成实时支持。Linux 6.12 起主线内核已有完整的 PREEMPT_RT 支持，但厂商内核是否可直接启用仍取决于具体分支和配置，不能直接假设兼容。

你的目标是先确认版本，再判断“已有 RT 配置可启用”还是“需要移植匹配补丁”，最后通过测试证明实时性，而不是只看到配置项就算完成。

### 3.1 SSH 是自带的还是需要添加？

SSH 是远程加密登录协议，通常由 OpenSSH 或 Dropbear 等用户空间程序提供。

- 内核层面：需要网络驱动、TCP/IP 协议栈等基础支持。
- Rootfs 层面：需要 SSH 服务端程序、配置文件、用户权限和启动服务。
- 发行版差异：有的官方镜像已经安装并启用 SSH，有的精简 Buildroot 镜像需要自己勾选并重新编译。

因此，不应直接修改内核来“加 SSH”。先检查系统是否已有 `sshd` 或 `dropbear`，再决定安装、启用还是编译进根文件系统。

### 3.2 Samba 共享文件夹

Samba 让 Linux 开发板通过 SMB 协议与 Windows 等电脑共享文件。你可以在 Windows 资源管理器中访问开发板的共享目录，方便传输程序、配置和日志。

Windows 电脑

以太网 / SMB 协议

RK3576：Samba 服务 + 共享目录

它同样主要属于用户空间服务和文件系统配置，不是一个独立的内核驱动。你需要配置共享路径、访问用户、权限和开机自启动，并保证网络连通。

### 3.3 固定 IP 地址

固定 IP 让开发板每次启动后都使用确定的网络地址，例如实验网络中的 `192.168.10.20`，便于电脑稳定地通过 SSH 和 Samba 连接。

静态 IP

在开发板的网络配置中指定 IP、子网掩码、网关等。

DHCP 地址保留

在路由器上为开发板的 MAC 地址固定分配同一个 IP，也能达到稳定地址的目的。

导师要求通常是希望你掌握静态 IP 的系统配置。具体修改 NetworkManager、systemd-networkd、ifupdown 还是 Buildroot 网络脚本，需要先看官方镜像使用哪种网络管理方式。

### 3.4 启动时 TTL 打印 Log 到电脑

这里的 TTL 通常指开发板上的 UART 串口调试接口（TTL 电平串口），不是网络协议中的 Time To Live。

RK3576 UART

TX / RX / GND

USB-TTL

串口转换器

电脑

串口终端

开机日志可以包含 Bootloader、内核启动信息以及登录终端。即使网络尚未配置成功，串口仍然可以帮助你定位系统卡在哪个启动阶段。

需要确认开发板的调试 UART 引脚、IO 电平（常见为 3.3 V，但必须看原理图）、波特率以及内核 `console=` 启动参数。USB-TTL 的 TX/RX 应交叉连接、GND 共地，绝不能把普通 RS-232 电平直接接入 SoC 的 TTL 引脚。

## 四、可执行任务清单

下面按照依赖关系排列，建议你逐项完成，每一项都保留截图、命令和验证结果。

1

确认开发板与建立开发环境

第一阶段：准备与资料

- 记录开发板完整型号、硬件版本、eMMC/SD 存储方式。
- 下载对应板卡的用户手册、原理图、SDK、官方固件和烧录工具。
- 确认 SDK 的 Linux 内核版本、发行版类型及工具链。
- 在 Ubuntu 主机或虚拟机配置交叉编译环境。
- 建立 `References`、`Study_Notes`、`Projects`、`Troubleshooting` 目录。

验收结果： 能准确说明当前板卡型号、SDK 来源、内核版本，并且所有资料可追溯。

2

烧录官方固件并建立串口调试

第二阶段：先保证系统可启动

- 根据板卡手册连接调试 UART 与 USB-TTL。
- 在电脑安装串口终端并设置正确波特率。
- 使用官方烧录工具将匹配的 IMG 写入开发板。
- 保存从上电到登录界面的完整启动日志。
- 登录系统，执行 `uname -a`、`cat /etc/os-release`、`lsblk`。

验收结果： 官方系统正常启动，电脑能看到 Bootloader 和 Kernel 日志，系统版本可查。

3

第一次完整编译与烧录

第三阶段：建立可重复构建闭环

- 阅读 SDK 的构建说明并确认板卡配置文件。
- 不修改任何代码，先完整编译一次。
- 找到生成的 Kernel、DTB、Rootfs 和完整固件 IMG。
- 将自编译固件烧录至开发板。
- 通过串口验证系统启动，并记录编译命令与产物路径。

验收结果： 不依赖官方现成镜像，能够从 SDK 生成可启动的系统。

4

完成一次可验证的源码修改

第四阶段：理解修改、编译与部署的关系

- 先在 Rootfs 中修改一个简单配置或启动脚本。
- 再尝试修改一处非关键内核代码，例如增加自定义启动日志。
- 重新编译对应组件并更新镜像。
- 启动后使用 `dmesg` 或串口日志确认修改生效。
- 使用 Git 提交修改并记录每次构建版本。

验收结果： 能证明“我改的源码”确实进入了开发板运行的系统。

5

配置固定 IP、SSH 与 Samba

第五阶段：实现远程开发环境

- 确认以太网驱动正常，电脑与开发板可以互相 ping 通。
- 查明系统采用的网络管理方式，设置固定 IP。
- 检查是否已有 OpenSSH/Dropbear，没有则加入 Rootfs 构建。
- 配置 SSH 开机自启动，并从电脑远程登录。
- 安装或编译 Samba，创建共享目录和访问用户。
- 在 Windows 中访问共享目录，测试上传、下载和权限。
- 重启开发板，确认固定 IP 和两项服务仍自动生效。

验收结果： 电脑能稳定通过固定 IP 访问 SSH 和 Samba，重启后无需手工重新配置。

6

研究并集成实时内核

第六阶段：内核定制与实时性验证

- 使用 `uname -r` 和 SDK 源码确认准确的内核版本及分支。
- 检查当前内核是否已经包含 PREEMPT_RT 支持。
- 查询板卡厂商是否提供匹配的 RT 补丁或实时内核分支。
- 若已有支持，启用对应配置；若没有，评估补丁版本与厂商代码兼容性。
- 保存补丁应用记录，解决编译冲突并生成新内核。
- 烧录或替换内核，验证实际运行版本及实时配置。
- 使用 `cyclictest` 等工具测量调度延迟，并与普通内核比较。

验收结果： 有可启动的 RT 内核、明确的版本和配置证据，并有量化延迟测试数据。

7

最终集成与交付

第七阶段：形成可复现成果

- 将 RT 内核、静态 IP、SSH、Samba 和串口日志配置整合到同一套固件。
- 从干净 SDK 或明确的 Git 提交重新构建。
- 烧录最终镜像并执行完整功能回归测试。
- 整理编译命令、修改文件清单、补丁、配置和测试截图。
- 输出最终 IMG、源码修改记录及一份操作说明文档。

验收结果： 其他人按照你的文档，可以重新编译、烧录并复现所有要求。

## 五、建议你优先掌握的命令

这些是进入开发板后最基础的检查命令，不涉及破坏性修改：

Bash

```
# 查看系统与内核版本
uname -a
uname -r
cat /etc/os-release

# 查看网络接口和 IP
ip addr
ip route

# 查看内核启动日志
dmesg | tail -n 50

# 查看磁盘与分区
lsblk
df -h

# 检查 SSH / Samba 程序是否存在
command -v sshd
command -v dropbear
command -v smbd

# 查看当前内核实时性配置（若内核提供该配置文件）
zcat /proc/config.gz | grep PREEMPT
```

如果系统使用 systemd，还可以使用 `systemctl status ssh`、`systemctl status smbd` 等命令；但精简 Buildroot 系统不一定有 systemd，因此需要先识别发行版，不能直接套用 Ubuntu 的所有命令。
