# SN100 上位机移植到 RK3576 的详细计划

更新：2026-10-22。目标是把当前提供的 Qt 上位机移植到 RK3576，在外接 HDMI 屏幕上通过 USB 键鼠操作，保持 SN100 所需业务功能、数据和通信行为一致。Windows 用于编码、界面与通用逻辑调试；电脑内的 WSL 负责 ARM64 交叉编译；RK 负责运行、实物验收及必要的远程调试。

**当前结论：具备继续开展移植准备的条件，尚不能判定完整软件可以在 RK 正常工作。优先建立 Windows 原版基线、落实 ARM64 算法实现、补全依赖，再决定 Qt 版本路线；目前不需要仅因版本不同就重新烧录系统。**

### 2.3 Qt 版本路线：比较后决策，不预先刷机

用户提出的两种方式都纳入评估。**建议先验证路线 B：保留 RK 5.15.13，源码同时支持 Windows 5.14.2 与 RK 5.15.13。**这是减少既有系统变更的工程判断；须由G1和代表模块验证后定版，不保证没有兼容问题。

| 比较项 | 路线 A：RK改用Qt5.14.2 | 路线 B：源码兼容5.14/5.15 |
| --- | --- | --- |
| 能减少的差异 | Qt API/部分行为差异 | 保留已跑通目标环境，并保持原Windows参考能力 |
| 仍然存在 | Windows/Linux、x86-32/AArch64、第三方库、ABI、字体/窗口/打印/设备接口差异 | 同左，另加两个Qt版本的构建与行为回归 |
| 实际工作 | 为现有aarch64系统交叉构建Qt5.14.2、全部模块/插件和依赖，适配现代工具链及图形栈 | 通用代码用5.14.2已有API；确需新版API时集中版本判断/适配；每个模块双目标构建 |
| 推荐实施范围 | 先应用私有目录隔离部署5.14.2，不覆盖系统5.15；启动脚本隔离插件/库路径 | 先固定Windows5.14.2/32参考与RK5.15.13；后续有条件增加Windows5.15.13验证配置 |
| 系统重烧 | 只有确需更换rootfs/BSP/显示依赖且私有部署不可行时才评估 | 首轮不需更换内核/rootfs |
| 主要风险 | 老Qt在Ubuntu24.04/GCC13及当前Mesa上的构建适配与维护成本；版本相同仍需全部功能验证 | 新增API/弃用警告、第三方私有API、DPI/插件行为不同；需持续回归 |
| 选择门槛 | 有证据表明B存在难以修正的Qt版本阻断，且A在代表功能上效果更好 | G1依赖成立，G2代表功能两端通过，无必须降级Qt的证据 |

- [ ] 设定最低源码Qt版本为5.14.2，记录C++标准；新API核对“since”。Qt版本差异使用 `QT_VERSION` / `QT_VERSION_CHECK`，平台差异使用 `Q_OS_WIN/Q_OS_LINUX`，业务型号差异使用产品配置，不混为同一开关。
- [ ] 兼容分支集中在平台/兼容层，避免页面内散布大量ifdef；每条分支都有实际构建与行为用例。禁止整段禁用算法、日志、LIS或导出来“兼容”。
- [ ] 分开构建目录、Kit、库路径、Qt工具和发布包；Qt5.15工具生成物不得未经验证混给5.14目标。更换Kit/Qt后清理对应可重建构建目录并重新qmake，不能混用旧moc/rcc/ui/obj。
- [ ] 若选A，先证明同一Ubuntu24.04目标sysroot中的glibc/libstdc++、DRM/GBM/EGL和输入插件兼容；不要复制旧发行版整套libc，也不要只复制某一个Qt SO。
- [ ] 若确需烧录，先核查实际写入的boot/rootfs/分区范围及受影响配置，再保存必要恢复材料到 `07_backups/qt_environment/`，大二进制用LFS、记录来源和SHA。内核/PREEMPT_RT、固定IP/SSH、Samba、设备权限、HDMI/USB按影响范围复测；不默认整机备份，也不假定原环境会保留。
- [ ] 形成版本决策记录：原版/目标准确版本与发行版补丁、模块、编译器、依赖、候选验证结果、选择原因、已知限制、回退入口。当前两条路线均未实际切换。

同版本能减少一类差异，无法消除跨系统和架构问题；Qt兼容说明不能解释为“编译成功后业务一定正确”。见 [Qt5.15发布说明](https://www.qt.io/blog/qt-5.15-released)与[二进制兼容边界](https://doc.qt.io/qt-6.8/qt-releases.html)。

- [ ] 启动日志记录QScreen名称、geometry/availableGeometry、物理/逻辑DPI、DPR、Qt版本和QPA平台；识别目标屏，而非始终拿第一块Windows桌面屏。需要响应屏幕变化时使用对应QScreen信号。
- [ ] 先把主窗、顶部状态、菜单、中央业务页和底栏纳入layout，定义伸缩/最小尺寸；保留objectName和信号槽。不要只调用showFullScreen，顶层填满屏幕不代表内部控件会重排。
- [ ] 业务页按可用逻辑区域建立标准/紧凑布局；表格按列优先级伸缩，密集设置/详情可滚动，关键结果、单位、报警、开始/暂停和退出始终可达；最低分辨率不足时明确提示或切换约定布局。
- [ ] 试剂盘、样本架、曲线等自绘区域用统一等比变换，绘制与鼠标命中共用正/逆映射；不做横纵独立拉伸导致圆孔变椭圆或点击错位。
- [ ] 临时保留绝对坐标的控件只从原始基准矩形重算，不对当前geometry连续累乘；检查动态创建控件、字体point与QSS px的组合，不直接推广当前Adptive辅助函数。
- [ ] 审查遮罩根、display_frame/view_frame与实际内容尺寸；将弹窗约束在目标屏逻辑可用区域，必要时内部滚动。不能把很大的遮罩根geometry直接当作内容窗口固定尺寸。
- [ ] 当前字体在UI和QSS中被多处显式指定；核实Linux实际family、字符覆盖、数字/符号和测量宽度。字体替换时同步核对表格列宽、按钮、报警和报告分页。
- [ ] Qt5高DPI属性在QApplication创建前统一设置；5.14/5.15和Windows缩放分别验证，禁止同时叠加多套全局缩放后凭单张截图确认。依据[Qt5.15高DPI文档](https://doc.qt.io/archives/qt-5.15/highdpi.html)。
- [ ] 测USB键鼠、Tab焦点、Enter提交、Esc取消、滚轮、组合键、中文输入及软键盘遮挡；当前软键盘850×320且是置顶独立窗，要在EGLFS上检验焦点/候选/收起；有物理键盘不构成删软键盘的依据。

| 验证环境 | 分辨率/缩放 | 地位与重点 |
| --- | --- | --- |
| Windows原版 | 1920×1080 /100% | 功能/显示参考，先核对原版实用尺寸 |
| Windows移植版 | 1920×1080 /100%、125%、150% | 同Qt跨DPI、文字/弹窗/焦点；像素增加不等于逻辑空间增加 |
| Windows移植版 | 1600×900 /100% | 与当前RK屏的布局对照 |
| RK当前HDMI | **1600×900** /实际DPI | 首轮必须通过全部约定页和弹窗、键鼠、曲线和报告 |
| 其他HDMI模式 | 1920×1080、1280×720；按需1366×768 | 仅EDID实际支持时验证；低分辨率是否列为正式支持范围需先确认 |
| 配套屏 | 型号/接口/分辨率/方向/触摸确认后 | 独立增加屏幕和触摸矩阵，不推定HDMI通过即可通过 |

**验收 G4：**正式支持矩阵每格均有页面/弹窗用例，无截断/覆盖/不可达操作/错位命中；信息和操作结果一致，布局可因空间重排。Windows模拟与offscreen测试不能替代HDMI现场验证。

### 3.5 阶段 G5：数据、外部接口与完整业务联调

- [ ] 明确只读安装资源与可写数据位置，消除对当前工作目录的隐式依赖；使用QCoreApplication路径/QStandardPaths或明确应用数据根。主程序、默认模板、可写配置、DB、日志、导出、备份各有边界。
- [ ] Windows路径/UNC/net use改为平台服务；同板文件直接访问本地数据目录，远程共享按真实需求配置。打印机、COM口与Linux `/dev/tty*` 用配置/稳定设备标识映射，不写死旧COM号。
- [ ] DB迁移先用匿名副本，核对schema/编码/列名/索引/精度/日期时区/事务/锁与busy超时；QSql连接和sqlite3连接分别审查线程与所有权，序列化模式不等于业务事务天然安全。
- [ ] 对MEMORY journal/synchronous=OFF提出保守持久性候选，比较回滚日志或WAL的可靠性与性能；核查实际文件系统/存储和备份方式，记录未提交事务/已确认结果允许丢失的边界。用测试库做进程终止/重启恢复，断电测试另按设备范围安排。[SQLite依据](https://www.sqlite.org/pragma.html#pragma_synchronous)
- [ ] 真机连接前明确SN100命令白名单/状态、控制器版本和现场条件；先只读状态查询，再在授权范围逐项启用真实动作。按设备记录TX/RX实际字节、响应/超时/退出码和实物现象。
- [ ] 完整流程覆盖普通/急诊/重复/稀释、校准、质控、暂停/恢复、试剂不足/缺校准/设备故障、掉线/重连、跨日和重启；禁止以模拟成功推定机械/采集通过。
- [ ] 打印和LIS用已确认型号/对端测试；先输出PDF对照，再实际打印，记录Linux驱动/后端；外部系统不可用时保持“待接口验收”，不删功能。

**验收 G5：**F清单约定范围全部有结果，关键状态/结果/持久化/报文正确，真设备各项有实物证据；无未解释的严重回归，剩余差异有明确责任、范围和处理决定。

### 3.6 阶段 G6：先测量再轻量化，不牺牲业务完整性

Windows和RK的快慢主要取决于实际CPU/GPU、内存、存储、散热和负载，不能仅凭操作系统判断。RK资源预算先做实际盘点，再给出可验收上限；目前没有完整应用的性能实测。

- [ ] 读取RK实际CPU/内存、可用空间、存储类型、温度/频率/降频、GPU渲染、显示模式、其他控制进程负载；记录仪器最大任务数/消息速率/曲线长度/历史条数和数据保存期限。
- [ ] 使用固定匿名数据量和同等功能场景，对比Windows参考与RK Release：冷/热启动、首次/再次开页、操作到反馈延迟P50/P95/P99、算法耗时、数据库/批量导出/打印、持续通信丢失及重连时间。
- [ ] 测整机与进程CPU、RSS/PSS和峰值、线程/FD、队列长度、磁盘增长/写入、温度；CPU记录注明单核或整机口径。先建立基线与预算（GUI、算法、控制、系统余量分别分配），阈值由业务需求和板上实测共同确定。
- [ ] 针对已有热点优化：取消无效GIF忙等，限制动画帧缓存；按测量减少阴影/全窗抓图/过度重绘；隐藏页面只暂停纯展示刷新，通信、告警、数据处理继续工作。
- [ ] 页面惰性构造需先把业务订阅从页面生命周期分离，避免未打开页面丢消息；图表展示可做保峰值抽稀/缓存，但原始曲线、算法输入和导出保留完整数据。
- [ ] 报告页已存在显示分页，进一步测DB查询范围、全量缓存、逐行控件创建和导出峰值；根据结果做查询分页/批处理/模型更新，不误称原版没有分页。
- [ ] 日志采用分类、轮转、有界缓冲与错误落盘策略，避免当前每次512KiB分配；记录真实TX/RX的同时控制高频展示。禁止静默丢失重要事件，明确背压/限流策略和敏感信息脱敏。
- [ ] 优化前后跑同一功能和负载用例，比较结果/报文/数据库一致性。先改局部瓶颈，后评估线程/进程调整，不为性能直接删功能或缩短业务数据。
- [ ] 同板控制场景测UI忙/曲线刷新/导出/LIS与RT控制并发；默认GUI普通调度，不给UI直接设SCHED_FIFO。断点和Debug不用于RT性能结论；指标与已有[实时内核计划](development_plan.md#preempt_rt-实时补丁与验证)衔接。
- [ ] 建议分级长稳：先连续2小时回放与反复开关页，再8小时业务负载，稳定后24–72小时；时长为待确认验证方案。检查内存/FD持续增长、队列积压、丢帧/丢任务、结果、日志容量、温度和退出恢复。

**验收 G6：**在约定最大负载和显示条件下，功能一致、资源有余量、性能/实时阈值达标，长期无失控增长；所有“降低了多少”都有同条件数据。单帧RGBA缓存约1920×1080×4≈7.9MiB、1600×900×4≈5.5MiB只是容量估算，不代表应用实测内存。

- [ ] 每包包含源码/构建版本、目标OS/架构/Qt/依赖、文件清单/SHA、配置和schema版本、启动与回退方式。Release可strip，调试符号在电脑按同一build-ID保存，禁止混用旧符号定位新程序。
