# 启动登录等待与历史记录忙状态：待整合候选

本目录只保存供下一轮整合的候选，不是新的正式源码或运行版本。此次没有修改正式源码、工程构建项、配置、账户或已有7c4abe30归档，没有操作板卡。正式集成03保持冻结；由整合会话在03匹配源码归档完成后串行处理本候选。

## 已从源码确认的问题

主窗初读标记齐全后只请求一次启动登录。若仪器连接配置仍在异步读取，登录入口会因“页面正在处理数据”拒绝；当前正式源码没有保存这次启动请求，后续页面空闲也不会自动重试。原版通过`login/open`控制单次启动登录，注销后另行打开登录卡。原版路径、当前调用顺序与文件指纹见`original_review.md`、`retry_audit.md`。

此外，历史记录的字典窗口也算页面忙碌，但关闭时原来只更新本页控件，没有向主窗报告综合忙状态。若它是最后一个阻挡登录的页面，单改启动重试仍可能一直等待。两项需一起整合，不能只套启动补丁。

这些是源码允许出现的确定遗漏；尚未在RK复现，也没有证据证明此前7c4abe30两轮检查正是因此失败。

## 登录请求的规则

- main仍只在原资料、密码登录、原配置`login/open`同时满足时登记启动请求，不从Guest身份猜配置。
- 启动请求与注销重登分别保存。页面忙时保留启动请求，等现有通知；最多排一个回调，没有轮询或立即重排循环。
- 请求回调执行时重新检查忙状态。真正进入原登录流程前即消费请求；拒绝离页确认、关闭登录卡或认证完成后都不会反复自动打开。
- 主动调用登录或注销入口立即结束旧的启动请求，即使该主动调用随后被忙状态或权限守卫拒绝。这里补齐的是公开入口约定；普通UI头像在忙时已禁用，本次未声称复现了忙时点击。
- 已有登录卡时只走原卡片流程，保留其认证、提示、关闭动画及密码规则。原版没有独立取消按钮，不新增按钮或改账户规则。
- 关机确认框仍打开时暂缓；取消关机后重新核空闲状态。确认关闭、窗口Close入口或应用退出会撤销启动请求；窗口已隐藏时旧回调不会再弹卡。
- Close入口的撤销时机是有意选择：即使后面的业务保护拒绝关闭，也不恢复旧启动自动请求，用户仍可主动点头像。原版在确认软关闭时解绑启动定时器；本候选没有把这项时机差异写成完全相同。

历史记录新增`busyChanged(bool)`是真实综合忙状态通知。子状态先改变再调用`setBusy`，因此与“上次已通知的综合状态”比较；不是比较刚进入函数时已变化的状态。只在综合真假变化时发信号，不发伪状态文字或伪成功回执。
