## 历史页面如何通知“仍在处理”

候选 `history/history_page.h:38` 的 `isBusy()` 只由三项组成：数据库操作 `m_busy`、报告操作 `m_reportBusy`、字典选择窗口 `m_dictionaryBusy`。登录等待的依据保持为这个综合结果。

逐项写入核对结果：

| 状态 | 写入及通知路径 | 结果 |
| --- | --- | --- |
| 数据库操作 | `history/history_page.cpp:938–941`，`m_busy` 唯一的赋值处在 `setBusy()`；查询、保存等调用该入口，结束操作在 `finish():991` 调用 `setBusy(false)` | 每次改变都进入综合状态计算 |
| 报告操作 | `history/history_page.cpp:704–707`，先设置 `m_reportBusy`，随即调用 `setBusy(m_busy)` | 数据库本身未忙，也会发布报告忙状态 |
| 字典选择窗口打开 | `history/history_page.cpp:749` 设为忙；同一函数在 `:796` 调用 `setBusy(m_busy)`，再在 `:797` 打开窗口 | 字典打开期间不会被误认为可登录 |
| 字典选择窗口结束 | `history/history_page.cpp:784–794`，清理窗口和未发筛选后，设为不忙并调用 `setBusy(m_busy)` | 字典关闭后的空闲变化有明确通知 |

`history/history_page.cpp:967–973` 把当前综合结果与 `m_lastReportedBusy` 比较，状态变化才通知主窗，并且在发送信号前先更新记忆值。这里使用“上一次已通知的综合结果”是必要的：报告或字典先改变成员，再进入 `setBusy()`；如果只比较进入 `setBusy()` 前后的实时 `isBusy()`，会错过这些变化。

若数据库操作结束但字典或报告仍忙，综合结果继续为真，不发假的空闲通知；最后一项结束时才通知空闲。重复的 `setBusy()` 调用也不会反复发送相同状态。

候选 `shell/history_shell.cpp:49` 接到通知后调用 `updateAccountStatus()`。后者在 `shell/frmmain.cpp:390–391` 先恢复注销重登，再恢复启动登录。两个恢复函数只排队一次回调，不在忙状态信号的调用栈中直接创建登录卡；回调再次核对忙状态。因此，历史页刚结束一项操作、同轮又开始另一项操作时，排队后的登录仍会被新的忙状态挡住。

页面挂入主窗前可能发生的初始通知也有兜底：`shell/history_shell.cpp:60` 在挂接完成后主动更新一次账户状态；启动登记时也会重新读取 `businessPagesIdle()`，不依赖曾经发送过的某一个历史信号。

## 启动、主动操作和退出的意图规则

`shell/main.cpp:562–563` 保留原条件：原项目模式、启用密码登录、原配置 `loginOpen` 为真时，才登记启动自动登录。`readyReported` 在 `:519` 先置真，启动就绪回调不会反复登记。

`shell/login_shell.cpp:38–84` 的三个状态分别表示“还在等”“已排队”“本次启动已消费”。它们与注销重登的两个状态分开，未借用注销标记补启动。

| 情况 | 候选行为与依据 |
| --- | --- |
| 启动时页面忙 | `resumeStartupLogin():65` 保留待弹意图；综合忙状态结束后重新检查，再排队 |
| 回调执行前又变忙 | `:78–79` 不创建卡片，保留原待弹意图，等后续忙状态变化 |
| 首次空闲后需要询问未保存内容 | `:80–82` 先消费启动意图，再调用原 `requestLogin()` 的离页确认；用户拒绝确认后不会反复询问 |
| 用户主动调用登录 | `requestLogin():124–127` 在权限、忙态和草稿检查前消费启动意图；即使公开调用在忙态被拒绝，也不会在空闲后由旧启动请求补弹 |
| 已有登录卡或登录成功 | `resumeStartupLogin():58–62,71–75` 发现已有可见卡或已认证身份就消费；主动请求也先消费，再抬起现有卡；不会另造一个启动卡 |
| 登录卡取消或关闭 | 显示前启动意图已经消费；卡片 `finished` 只清指针、延迟删除和更新账户显示（`:159–167`），没有重设启动待弹状态 |
| 用户主动调用注销 | `shell/frmmain.cpp:412–415` 在其他守卫之前消费旧启动意图；本次调整不清空或复用注销重登状态 |
| 注销完成 | `shell/frmmain.cpp:403–408` 根据实际身份清除结果登记独立重登；`resumeLoginAfterLogout():119–120` 在真正发起请求前消费该重登意图 |
| 打开退出确认框 | 启动回调发现确认框存在时暂停保留（`login_shell.cpp:65,79`），不会与退出确认一起弹登录 |
| 取消退出确认 | `shell/frmmain.cpp:602–605` 调用 `updateAccountStatus()`，同时恢复仍待处理的注销和启动意图；已经消费的启动意图不会重新登记 |
| 确认退出 | `shell/frmmain.cpp:608–611` 先标记退出并消费启动意图，再关闭外层窗口 |
| 直接关闭窗口 | `shell/frmmain.cpp:619–622` 在关闭事件入口消费；即使后续业务保护拒绝退出，本次启动意图也不再恢复 |
| 真正离开应用 | `requestStartupLogin():42–43` 接应用退出通知来消费意图；排队回调还检查 `shutdownClosing_` 和外层窗口是否可见（`:71–75`）。注销回调也增加了可见性检查（`:109–112`），避免窗口已隐藏后又创建重登卡 |

把 `cancelStartupLogin()` 移至主动登录和注销入口符合这次明确要求。“主动调用”本身已经取代尚未显示的启动请求，不必等到业务守卫通过才承认该意图。自动启动在调用 `requestLogin()` 前已消费，重复消费没有其他动作；注销重登调用它也不会改变注销自身的状态。

这里的“旧意图不补弹”特指旧启动自动请求。注销完成后重新登录是独立行为，仍保留。没有把“取消启动自动登录”扩大成禁止后续注销重登。

## 原版源码依据及明确差异

原版路径以 `06_programs/sn100_host_reference/Seerain450_PC/` 为起点：

- `frmmain/frmmain.cpp:296–307`：原配置 `loginOpen` 决定是否把启动定时器接至 `slotShowLogin()`；定时器为单次，启动延迟 100 毫秒。
- `frmmain/frmmain.cpp:673–687`：`slotShowLogin()` 创建一张卡，调用 `showDialog()`，返回后延迟删除；没有重新登记启动请求。
- `frmlogin/maskdlglogin.cpp:122–142`：`showDialog()` 显示动画后进入对话框；`closeDialog()` 只启动关闭动画。原界面没有单独的取消按钮，`:56–73` 还拦截 Escape，不能将“原有取消按钮”作为依据。可确定的是原调用路径没有关闭后自动重开的循环。
- `frmmain/frmmain.cpp:2077–2093`：注销清空权限和显示名，发送注销信号，再直接调用 `slotShowLogin()`；它不依赖启动定时器。
- `frmmain/frmmain.cpp:641–668`，特别是 `:653–661`：确认退出后断开旧登录定时器，改接应用退出；取消退出确认不会走这段断开逻辑。

本候选的忙时等待，是为异步初始化保留原“一次自动打开”的意图；原版没有这套异步等待状态。另有一项主动选择的差异：候选在任何关闭事件入口就永久撤销启动意图，即使关闭被业务保护拒绝；原版在确认退出后才断开定时器。这符合本轮约定，但不能写成与原版逐字一致的关闭时机。
