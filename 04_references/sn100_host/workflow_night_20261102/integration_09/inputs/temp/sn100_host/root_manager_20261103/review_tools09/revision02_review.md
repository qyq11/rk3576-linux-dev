## 核心对应规则

`integration_09_object_binding.py`不执行shell来猜数组。它只接受能完整识别的声明数组、有限的路径变量和`.cpp/.h`通配；按真实声明顺序与实际TSV列表逐项比较，再比较规范化后的完整生成、编译及链接控制骨架。控制流程未知、源表缺输入、重复命名或实际集合不等时拒绝。

本次独立读取实际正式 `shell/build.sh`，按相同规范化规则与工具的只读字面模板比较，结果完全相同。此静态操作仅解析文本与常量，未导入或执行作者工具。11份QRC的105条直接资源引用逐条核查均被当前684份完整表覆盖。

- 主对象顺序是实际普通源、含Q_OBJECT的头所生成的moc源、QRC顺序生成的rcc源，与冻结构建脚本一致。每项记录实际对象SHA/大小、源文件SHA/大小、原冻结直接输入和链接角色。
- moc/rcc/uic生成文件均保存实际SHA。moc对应冻结头，rcc对应冻结QRC及其文件条目，uic头对应冻结UI；实际生成文件集合必须完整相等，不能用数量代替。所有冻结源码本身也逐份核SHA。
- 报告程序先按原辅助源选择条件复用主对象，再按真实供应商moc循环和独立helper输入构造链接清单；没有把所有GUI对象写成报告对象，也没有按文件名字样随意猜测。
- 对象均核ARM64可重定位ELF，两份程序核ARM64程序ELF；对象、生成文件和整个本批构建目录普通文件实际SHA进入稳定绑定。绑定不带会导致每次重建变化的时间戳。
- 相同记录口径使用项目根相对路径，WSL `/mnt/c/` 路径在Windows读取时转换为实际本地路径，生成的记录仍保持相同相对路径；入口延迟读取共同上下文，没有循环导入时执行阶段。
- `verify_binding`重新读取现物、重建完整JSON并严格比较，既比较SHA，也比较来源和链接角色。不是仅检查原绑定文件自己的SHA。

## 各阶段的强制引用

1. 打包后 `verify_integration_09_inputs.py`建立本批 `object_binding.json`，`build_complete.json.object_binding`保存其record；没有完整绑定就不会生成成功终态。
2. `integration_09_tool_support.verify_build()`核固定位置、实际绑定record并重新重建比对；stage在SSH前和结束后调用这条检查。因此对象或源在构建后变化不能直接进入板端暂存。
3. archive将绑定原文复制到正式恢复目录，provenance记录原件和副本SHA，复制后及收尾前重新核构建绑定；archive_complete保留绑定record。
4. collect核WORK与正式归档绑定逐字节相等，证据根保存同一原文；object_inventory现在保存真实对象SHA和对应绑定条目。复制前后继续重核。
5. finish核WORK、正式归档、证据三份原文及各完成凭据引用，最后再复核实际对象绑定，才生成最终完成记录。
