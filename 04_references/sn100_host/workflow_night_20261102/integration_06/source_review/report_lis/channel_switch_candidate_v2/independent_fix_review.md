## 原问题怎样被修正

`candidate/shell/main.cpp:1226–1244` 新增统一通知函数。每条结果先保存到通道页的 `originalChannelResult`、请求号、连接代次、结果名、页面刷新标记及页面自身 tooltip，再发原 `statusChanged`。原 `instrument_shell.cpp:86–90` 在存在 DeviceControl 时直接返回，因此该信号本身仍不承担全局可见提示；本版另有明确的非模态 `QToolTip::showText` 路径，补齐了 v1 缺口。

真实终态与文字对应如下：

| 回执 | 本次核对 |
| --- | --- |
| `Failed` | 明确“未保存”，附后台原因；失败路径不再仅留日志。没有改成成功或自动重发。 |
| `CommittedReloadFailed` | 明确“已保存，但重新读取失败，页面尚未刷新；需重新读取核对”。不承诺关闭后仍会继续重读。 |
| `Committed` | 只有接收器 `displayed=true`，且通知当时控制对象仍已连接、代次相同，才说当前表已刷新并清除旧 AD。否则明说未刷新；旧代说明旧连接已经保存。 |
| `Cancelled` | 明确“已取消，未保存”；接收器给未派发/已撤销批次及后台真实取消结果使用该终态，未改许可或事务路径。 |
| `Unconfirmed` | 落入明确“保存结果待核，未确认完成，不会自动重放”，不把线程结束前未消费的回执当作回滚或成功。未知结果同样保守表述。 |
| `Receiver.error` | 也接到统一通知路径，原错误不再只发被宿主跳过的 `statusChanged`。 |

`main.cpp:1262–1263` 复核当前连接后的 `refreshed` 才写入页面刷新属性。该属性表示资料是否在本次连接被页面消费，**不是操作者是否看见浮动提示**。页面消费原方法仍在 `instrument_page.cpp:1043` 起核 GUI 线程、当前连接代次和资料身份后才重建；本版没有挪动清旧 AD 时点。

`snapshotRecovered` 单独在 `main.cpp:1280–1295` 处理真实重读恢复，并再次核 `displayed` 与当前代次。如果回执说曾刷新、但提示前连接已经变化，就说明“连接在显示结果确认期间已变化”，不附带旧的“当前已刷新”断言。接收器 `consumeRecoveredSnapshot()` 消费并清空恢复归属，只发 `snapshotRecovered`，没有再发 `batchFinished`；本次 delta 也没有增加第二次提交或第二批终态。

退出时接收器仍保留 v1 的 `stopRequested_`、撤销及排空路径；`reloadIfNeeded()` 明确拒绝停止后的重读。新提示用“需重新读取核对”，没有把它说成退出后仍在进行的工作。保存/撤销/待核事实仍由原 worker 回执决定，通知函数不写业务库。

## 可见性和原界面保持

- 浮动提示只在主窗实际可见且 `window()->isActiveWindow()` 为真，并且 `statusArea` 可见、可见区域非空时调用。锚点取原全局状态区，通道页隐藏时也不切页。
- 失焦或不可见时仅保留页面属性/自身 tooltip，不补弹，也没有重新激活监听。应如实记为“保存了可供查看的结果”，不能说失焦期间已经显示给操作者。页面自身 tooltip 能否在具体鼠标位置触发仍需现场核对。
- 只以 `statusArea` 定位，没有对它调用 `setToolTip`、`setText` 或 `setStyleSheet`。实际设备状态、灯色及其原设备/医院提示保持原消费者；`page->statusChanged` 在 DeviceControl 存在时也不会覆盖主状态区。
- 浮动文字经过 HTML 转义；没有 `exec/open` 消息卡、模态遮罩、`setFocus`、`activateWindow`、`raise` 或导航操作。`QToolTip` 的实际显示位置、遮挡和持续时间仍需 RK 核对。
- 结果属性及页面自身 tooltip 保留最近一次通知；后续通知会替代最近结果，不是多批持久通知历史。完整批次日志仍保留。该行为及“活跃窗口才显示、失焦不补弹”已由 handoff 明确列为相对原提前成功弹框的界面差异。
