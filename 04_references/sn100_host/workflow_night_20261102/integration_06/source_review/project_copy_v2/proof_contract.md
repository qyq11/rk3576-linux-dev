# 已证明未提交：持久状态的条件

用途是保留“这份自有克隆当时没有提交”的已核事实。否则一次已回滚复制预留过的校准号，被后来正常CAL（定标任务）再次分配，下一次读取就会把本来可过滤的克隆误判成unknown，重新挡住样本、试剂、历史与项目同步。

这里写的是候选源码合同，没有创建或运行测试库、没有操作真实marker/项目库。v1原件保留，本目录是独立v2。

## 第一次必须完整证明

仅从有完整目标身份的prepared或ready阶段进入。仍按v1先让SQLite正常热journal恢复，再持有项目/试剂QLock及目标main+两个附加库的BEGIN IMMEDIATE核对事务，确认：

- 清单格式、工作根、源/目标命名、旧/新编号、源/目标和附加库身份、自有普通文件与私有权限都可核。
- 目标仍是同一自有文件，完整数据库指纹与初始克隆相同，内部仍为旧项目编号/名称。
- 源文件身份和原版本未变；新项目名在base/binding/group均无关联；本次预留校准号在base/binding/data均为空。

不是只比较初始SHA就首次放行。creating尚无目标身份、缺base、部分关联、身份不符等情形仍unknown，不补造曲线或猜新项目。

全部成立时，才把原清单原子改为`phase=uncommitted-proven`，附`sn100-uncommitted-copy-proof-v1`对象。对象记录原prepared/ready阶段、UTC核对时间、完整清单的证据SHA和已执行的核对项。证据SHA绑定原根、源版本与身份、目标身份/完整克隆指纹、编号/名称、附加库身份、预留编号以及ready原行证据；不是拿它签发写权限。

## 落盘及后续复核

原子QSaveFile发布后，显式打开同一marker文件描述符：fstat核本用户、单链接、普通文件及dev/inode，与已核路径身份一致，再检查fsync和close返回值，重核路径身份并同步父目录。随后重读marker，核字节与预期完整对象、读取前后身份；目标身份/完整指纹再次核对。以上仍在SQLite核对事务和两把QLock持有期间，完成后才结束核对事务并交出排除文件名。

不依赖“Qt通常会同步”来宣布证明已落盘。文件同步、目录同步、原子发布、重读或目标复核任一步失败，当前调用不排除克隆，保留现场并报待核。若文件已经原子发布但同步未确认，下一次即使读到完整proof，也要重新显式同步同一自有fd并核全套条件后才能读取放行；同步继续失败仍拒绝。

以后每次读取都重新核：私有marker结构/内容与证据绑定、同一自有目标文件身份、完整初始克隆内容、内部旧编号/名称、原附加库身份及新项目名仍无关联。目标缺失、替换、内容改变、新名有关联、proof字段/内容不符或无法落盘复核，均unknown；不按证明去清理或回退。

已经持久证明后，**不再因预留校准号被别的合法CAL使用而推翻历史未提交事实**，也不重新要求源还保持旧版本。源当时的版本/身份已在证明中绑定，目标历史克隆仍逐次核完整内容；源后来发生什么仍由正常项目读取/版本保护处理，不能拿克隆充当缺失源或新项目。

## 仍然不能做什么

证明不修改目标DB、校准/试剂行或计数器，不授权项目写入、删除或移动。所有项目写入口仍因marker而拒绝。已完整提交仍沿ready完整提交核对，保留数据，只收尾元数据；新proof不会把已提交项目当未提交。证明是本程序私有清单内的完整性记录，不是对任意同用户伪造元数据的认证签名。

恢复mutex只串行多个恢复读者；项目/试剂QLock均try0，写入口纯查pending，不带写锁去等待恢复mutex。并发改变无法核对时明确拒绝，不借重试去放宽身份或关联条件。

源码保证与fsync/SQLite实际故障恢复效果分开：本轮仅对象编译和只读复核，未验证断电、磁盘错误、热journal恢复、CAL号复用或应用重开。需要按Root获准的RK真实范围核对，不用模拟或本机产品运行代替。
