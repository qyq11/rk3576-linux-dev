# SN100 上位机功能与 Linux 移植分析

原全量核查：2026年10月26日18:27；本地功能状态补充：2026年10月27日06:18，Asia/Shanghai。阅读对象：准备学习、接手和修改本工程的开发者。后续验证状态按同一功能账和移植记录更新。

当前 Linux 版已经形成一个统一的上位机，可以在电脑上完成医院与账户管理、项目和试剂配置、样本任务预设、历史报告处理、质控资料管理、校准原始点管理等本地业务。它还没有完成“连接真实仪器 → 下发检测任务 → 得到真实结果 → 计算并审核 → 上传和打印”的整条流程。

与原 Windows 版相比，主要工作是保留原页面和业务字段，逐模块提取所需代码，把数据库、界面、通信和报告处理的职责分开，再补 Linux 构建、离线测试及部署工具。原 Windows 工程完整保留在参考目录；未搬入正式工程的代码，不能直接算作已经删除的业务。

本文件用于理解功能和代码变化。日常执行顺序仍以[移植计划](../plans/sn100_host_migration_plan.md)为准；实际操作与测试结果统一查[移植记录](../../02_records/20261022_sn100_host_migration.md)，不在这里建立第二套开发计划。

## 一 整个上位机做什么

### 上位机在仪器系统中的作用

上位机是使用者看到、操作的程序。使用者在这里配置项目、安排样本、查看状态、处理结果和生成报告。仪器中的执行部件负责加样、移动、测量等动作，二者通过约定的通信消息交换任务和结果。

完整业务可以按以下顺序理解：

1. 维护基础资料：医院、操作者、分析项目、单位、试剂和检测方案。
2. 准备检测：配置校准和质控资料，登记样本所在架、孔位以及要测的项目。
3. 执行检测：检查准备条件，下发任务，处理开始、暂停、恢复、急诊和异常。
4. 处理结果：接收原始数据，计算、校准和判断结果，保存可追溯记录。
5. 输出结果：查询报告、生成文件、上传医院信息系统、打印。
6. 维护设备：查看状态、处理告警、记录维护，执行获准的设备维护动作。

当前已经做得较多的是第1步，以及第2、4、5、6步中可以脱离仪器完成的部分。第3步和真实数据的计算、校准、质控判断，是后续形成完整系统的关键。

原主界面有8个主要业务入口；用户设置内有账户、医院、语言、打印机、LIS共5个子页。统一启动器的`integrated-run`已经默认接入上表主要本地页面和告警历史；状态文件回放、本机模拟状态仍需显式选择。界面的开始、暂停和恢复控件目前保留并禁用，不能用于实际检测。

报告这里的“恢复”指取消草稿、恢复默认排序或失败回滚；当前没有找回已隐藏报告的入口，不能把它写成隐藏报告恢复已实现。该入口是否属于原版实际启用范围仍需对照。

“LIS”是实验室信息系统，也就是仪器向医院系统接收任务、上传结果所连接的服务；当前有本地设置和离线原报文辅助收件箱，尚无完整任务下载和结果上传，导入原文也不会自动生成检测任务。

几个容易误解的操作需要单独说明：

- 样本“复位、复测”目前改变本地草稿，明确更新设置后才写入；它不会让真实仪器立即重新检测。相关实现见[sample_task_reset.cpp](../../06_programs/sn100_host/samples/sample_task_reset.cpp)和[SamplePage](../../06_programs/sn100_host/samples/sample_page.cpp)。
- 校准记录“保存成功”表示原始点已经存好，选中曲线不会使它进入结果计算。“反算值”目前没有计算。
- 质控管理里保存规则选项不等于已经执行失控判断。原历史点缺少逐点单位证据时，页面显示单位未知，不使用当前项目单位补填旧结果。
- 报告“打印”入口的指定设备及标准确认接线已写，缺设备失败链已有验证，但没有正向系统提交或出纸证据。新原值结果模式仍不开放预览/文件输出，不能把按钮名称当作已通过的输出方式。
- 当前结果配置只解释“现在已提交的项目资料”。它不会改写四个原始结果字符串，也不能补出检测当时缺失的单位；真正的检测时快照和仪器结果来源仍需接入。
- 告警历史库默认位于显式数据根的`alarm_history/abnormal_log.db`，缺失时提示不可用，不自动造出历史记录；实时告警与历史查询是两件事。

### 还有两类独立研究工具

| 工具 | 用途与当前结果 | 与正式业务的关系 |
| --- | --- | --- |
| 统计工具 `quality/` | 用固定数据计算均值、标准差和变异系数，用于核对统计公式及异常输入 | 它和`quality_control/`质控业务页不是同一个模块；公式验证不代表真实质控规则已经实现 |
| 凝血点研究 `coagulation/` | 用百分比法和最大一阶导数法，从合成曲线寻找候选凝血时间，并明确返回失败原因 | 新研究原型，没有替代供应商AL4A全部算法，也没有接患者报告或仪器控制 |

变异系数用于描述一组测量值相对平均值的离散程度。凝血点则是从测量曲线中确定一个时间位置；两者都需要先明确单位、输入和业务方法，不能看到一个数值就判断临床可用。

## 二 对比 Windows 系统改了什么

### 对照范围和工程关系

原参考工程入口是[SeeRain450.pro](../../06_programs/sn100_host_reference/Seerain450_PC/Seerain450_PC/SeeRain450.pro)。虽然目录和工程名含450，本项目仍须按SN100实际配置判断启用范围，不能把其他机型的同名命令或页面直接当作SN100功能。

正式统一程序入口是[shell/main.cpp](../../06_programs/sn100_host/shell/main.cpp)，构建入口是[shell/shell.pro](../../06_programs/sn100_host/shell/shell.pro)和[shell.pri](../../06_programs/sn100_host/shell/shell.pri)。根目录的[sn100_host.pro](../../06_programs/sn100_host/sn100_host.pro)仍主要服务早期医院和账户独立入口，学习整个系统时应先看`shell/`。

目前保留Qt5 Widgets界面框架、qmake构建方式和C++14。原Windows基线为Qt5.14.2和MinGW32，WSL离线环境为Qt5.15.13与x86_64，RK候选为Qt5.15.13与ARM64。正式源码可以分别编译为Windows、电脑Linux和RK程序，各平台的对象和依赖库隔离；这不是只保留Linux单平台的重写。

### 主要代码改造

| 改造点 | 原Windows参考方式 | Linux正式工程的处理 | 对学习和使用的影响 |
| --- | --- | --- | --- |
| 工程接入 | `SeeRain450.pro`包含大量页面、公共对象、通信和第三方依赖 | `shell.pri`按功能显式包含各`.pri`和主壳接线文件；各业务保留独立入口 | 可先理解一个模块，再看它怎样接入整套程序；缺席的原目录需核查是否尚未搬入 |
| 全局对象和启动副作用 | `frmmain.cpp`在登录前创建通信对象，可能打开设备TCP和LIS；业务较多依赖公共状态 | `shell/main.cpp`按参数建立各工作对象，显式要求数据根；默认访客；没有自动使用参考配置连接仪器 | 启动离线程序不会自动执行原生产连接；状态来源和操作权限分开 |
| 页面与数据库 | 原页面依赖`SystemCommon`、表对象和全局数据库辅助层 | 页面发信号，Store在所属工作线程处理SQL，再用值对象返回结果 | 点保存后要等真实提交成功再更新界面；界面、SQL和错误路径可以分别阅读 |
| 数据库可靠性 | 原`sqlite_helper.cpp`默认`MEMORY`日志及`synchronous=OFF` | 新Store采用参数绑定、事务、显式错误和线程检查；例如HospitalStore设`DELETE`日志和`FULL`同步 | 已改进的模块要按各自Store核对，不应假定所有库同一策略或已完成断电验证 |
| 引用关系 | 原业务较多依靠名称及共享状态关联 | 项目、试剂、样本有事务和引用检查；质控、校准有跨库保护登记、UUID、路径绑定及启动对账 | 可以阻止误删被使用的资料；两个数据库仍分别提交，不是一次跨库事务 |
| 账户与会话 | 原登录、角色和账户表与全局业务耦合 | `AccountStore`提供本地认证和会话，主壳向页面传递状态；账户、项目等已接入权限控制的写操作，在数据侧也做核查 | 界面禁用之外有数据层检查；当前仍保留原`pwd`直接存储和比较语义，未完成密码安全升级 |
| 通信 | 原`communication/`、命令线程、LIS线程与主界面强耦合 | 新`protocol/`拆分帧编解码、状态、只读消息、TCP传输和客户端；先验证回放与自建回环 | 能独立检查拆包、超时和重连；只读诊断成功不能证明可执行检测命令 |
| 报告 | 原报告页、数据对象和QtRPT调用联系紧密 | 新历史存储、报告数据快照、渲染和控制器分开；保留QtRPT和原模板；新增独立PDF辅助进程 | 较重导出可以受超时和失败管理；模板、数据和导出链能分别追踪 |
| 中文显示和PDF | 依赖原字体、Windows运行环境及报表库行为 | 增加可用字体选择、中文映射核对与报表库本地补丁 | 中文“显示出来”和PDF中可搜索、复制是不同检查；字体变化仍需版面对照 |
| CSV和HTML | 原工程链接qtcsv等Windows库；报表还有不同导出路径 | CSV以源码处理GBK、引号与换行，不能表示的字符明确拒绝；HTML通过控制器生成UTF-8文件并处理保存失败 | 无需直接使用原Windows CSV DLL；原Windows实际引号等行为仍待对照，不能仅凭编码相同判断字节等价 |
| 页面适配 | 原主界面初始1920×1080，很多子页1751×968，较多绝对坐标 | 保留原画布及控件位置，在小宿主外侧滚动；替代不可用字体；保留原颜色和图标来源 | 1600×900先保证可达；这还不是触控小屏适配完成，也不是全面重设计 |
| 绘制与资源 | Material控件透明halo仍可能反复安排无效重绘 | 修复无可见贡献的重绘，保留原时钟和动画行为 | 同条件WSL短观测有CPU改善；不据此推算整套程序RK资源 |
| 构建部署 | 原版主要依赖Windows工具链、DLL和工作目录 | 新增WSL、Windows、ARM构建与运行封装、动态库检查、SHA校验、匹配恢复归档 | “源码、产物、依赖、测试结果是否同一批”成为可核查内容 |
| 测试 | 原参考工程没有当前这套模块化离线验收链 | 新增匿名夹具、存储与页面测试、跨模块回归、通信诊断及资源观察工具 | 测试工具不是临床业务模块；通过范围需和输入、版本、环境一起阅读 |

统一程序仍包含报表所需的QML、Charts、打印、网络、SQL、XML和SVG等依赖。`shell.pro`中的初始模块列表不是最终依赖清单，后续`.pri`还会引入依赖；不能因此推断程序不使用网络库或只剩几个基础Qt库。

代表性代码可从以下位置直接对照：

- 原医院页`frmuserset/frmhospinfosetting.cpp`，对照新[frmhospinfosetting.cpp](../../06_programs/sn100_host/ui/frmhospinfosetting.cpp)与[hospital_store.cpp](../../06_programs/sn100_host/data/hospital_store.cpp)。前者管输入和显示，后者管校验、事务及提交结果。
- 原`frmsystem/frmsystemmaterial.cpp`，对照新[projects_store.cpp](../../06_programs/sn100_host/projects/projects_store.cpp)；原`frmreagent/frmreagentmaterial.cpp`，对照新[reagent_store.cpp](../../06_programs/sn100_host/reagents/reagent_store.cpp)。重点看保存前的引用检查和失败回报。
- 原`frm_report/frm_report_material.cpp`，对照新[history_page.cpp](../../06_programs/sn100_host/history/history_page.cpp)、[history_store.cpp](../../06_programs/sn100_host/history/history_store.cpp)与[report_controller.cpp](../../06_programs/sn100_host/history/report_controller.cpp)。
- 原`frmcalibration/`和`frm_quality/`，对照新[calibration_store.cpp](../../06_programs/sn100_host/calibration/calibration_store.cpp)与[qc_store.cpp](../../06_programs/sn100_host/quality_control/qc_store.cpp)。这里保留和新增的是本地记录及保护机制，完整计算和临床规则仍有缺口。
- 原`customtools/AL4A_Driver.cpp`与`algorithmcore.cpp`，对照新[clot_endpoint.cpp](../../06_programs/sn100_host/coagulation/clot_endpoint.cpp)。后者是独立研究实现，不能作为前者全部函数的替换证明。

每个业务目录中的`origins.json`等来源文件可继续追原表单、字段、规则和有意差异；正式验证结果仍以对应记录及证据为准。

### 增加了哪些模块和工具

“新增”要分业务能力和工程支持。下面有些目录承接原业务，有些才是原版没有的支持机制。

| 正式位置 | 新增或重组内容 | 属性 |
| --- | --- | --- |
| `shell/`及各`*_shell.cpp` | 统一离线启动、模块接线、会话、草稿守卫和关闭管理 | 对原主界面集成方式的重组 |
| `data/` | 医院、账户、打印设置、LIS设置等Store及报告字典请求值对象 | 数据职责拆分及异步接口新增 |
| `projects/`、`reagents/`、`samples/` | 原项目、试剂、样本页面及本地存储；增加明确的事务、引用和草稿边界 | 原业务提取与可靠性改造 |
| `quality_control/`、`calibration/` | 本地元数据、历史读取、原始点、单位快照和跨库保护 | 原业务的分阶段实现及保护机制新增 |
| `alarm_history/` | 独立只读告警历史Store、页面和宿主 | 原历史查询业务重新组织 |
| `history/`中的字典与报告控制器 | 已提交医院字典选择、报告快照、隔离导出、HTML与显示设置 | 原业务补齐和输出链改造 |
| `protocol/` | 可独立运行的编解码、只读客户端、TCP传输、文件回放和自建回环 | 现阶段通信实现与诊断工具新增 |
| `quality/`、`coagulation/` | 统计和凝血点研究 | 独立研究工具新增，未作为临床结果引擎 |
| `tests/`及业务内测试目录 | 匿名固定输入、错误恢复、跨模块引用、页面与通信验证 | 开发验证支持新增 |
| `build.sh`、`wsl.sh`、RK脚本与检查打包工具 | 三平台构建隔离、依赖闭包、部署核验和恢复输入配对 | 构建交付支持新增；Python脚本用于开发机工具，不代表板端业务靠Python运行 |

### 哪些没有搬入或没有启用

| 原版内容 | 当前处理 | 应如何理解 |
| --- | --- | --- |
| `SystemCommon`、原命令线程和大范围全局业务对象 | 正式主壳不整套加载，由模块Store和接线承接已实现业务 | 结构替换；尚未承接的原业务还需要逐项分析 |
| 原设备TCP与机械控制、开始暂停恢复任务链 | 不在离线主壳启动时自动启用；真实动作禁用 | 尚未移植或尚未验收，不能登记为无用代码删除 |
| 原`commlis/`、`comHL7/`活动通信 | 本地设置已迁，实际收发链没有整体接入 | 后续需要完成协议和端到端联调 |
| AL4A Windows32算法DLL和驱动 | 未作为Linux算法引擎加载 | 架构不兼容且实现材料不足；研究原型不能覆盖原计算范围 |
| GL4A Windows日志DLL及Windows崩溃接口 | 不直接带进Linux依赖；现有模块使用可用诊断输出 | 当前输出已能支持专项取证，完整原日志与崩溃能力仍须对照补齐 |
| QtXlsx、qtcsv的Windows DLL | 不加入Linux运行库；CSV已有源码路径，XLSX未开放 | 有实现替代或功能暂缺，不能简单称删掉两个完整业务模块 |
| Windows专用共享目录、DLL加载和DbgHelp路径 | 没有沿原实现直接进入当前Linux主程序 | 需要按实际需求提供平台替代；不是复制原系统配置即可工作 |
| task、formula、估时和其他机型分支 | 原版存在部分未接菜单或未启用调用；当前未全面开放 | 先确认SN100实际发行范围；源码存在不等于原版可用，也不等于应删除 |
| 原软键盘和全局事件过滤链 | 当前没有整体等价接入原实现 | 电脑上的中文输入已有环境方案，RK触摸、软键盘、焦点与自绘点击仍需专项核查 |
| 英文切换 | 原语言页仅中文，Apply原本为空；新页明确反馈不可切换 | 当前不是多语言系统；原来没有实现的能力不能算移植退化 |

本次没有删除任何源码，也没有清理参考工程。以上是代码接入和行为边界分析，不是逐文件删除清单。现有材料不足以给出“原工程有多少行已被永久删除”的可靠数字：提取、拆分、重写和未迁内容混在一起，直接比较目录数量会误导。

确有明确减少的部分包括：不再将原Windows二进制、历史生产数据库、旧连接配置和个人IDE配置整包带入正式工程；已验证的无效绘制被修正。前者是依赖和运行输入范围缩小，后者是实现优化，都不代表允许缩减用户需要的检测业务。

源码中的小范围调整还包括复制后的Material控件去掉无用`systemcommon.h`引用、修正无效颜色写法以及资源路径改用QRC。这些应记录为具体实现改动，不能扩大成“原公共模块已证实全部无用”。

### 有意改变的行为

| 操作或场景 | 现在的行为 | 原因及后续要求 |
| --- | --- | --- |
| 启动程序 | 需要显式运行数据目录，默认访客，按参数启用功能；模拟状态不解禁机械动作 | 建立离线和真实运行边界；未来生产入口需重新明确连接和就绪条件 |
| 未保存就离页、注销或退出 | 处理继续编辑、取消和放弃等分支；在途保存和导出受守卫约束 | 避免丢草稿和半途释放对象；新增模块需补全统一退出路径验证 |
| 读取旧质控点 | 单位证据未知就显示未知，不套用当前单位做统计 | 防止历史值被后来修改的配置误解释 |
| 复制或删除校准记录 | 保留历史快照，删除为软隐藏，仍保护被引用内容 | 保持记录可追溯；尚不提供拟合审核和应用 |
| 点语言应用 | 原空回调改为异步提示仅支持简体中文 | 不让空操作看起来像成功保存；弹窗生命周期也需测试 |
| 读取告警历史 | 明确现存本地只读来源，缺失报不可用 | 不从参考包加载旧生产历史，也不生成虚构告警 |
| HTML导出 | UTF-8、新文件、取消不落盘；源文字含`&`时明确拒绝 | 当前已知限制，后续应补正确转义并验证，不应改坏用户资料来绕过 |

## 三 后续建议更改什么

### 先完成当前整合与真实检测闭环

优先级应由依赖和影响决定。继续增加能保存的页面，并不能自动得到一台能正确检测的系统。当前最需要的是让既有功能在同一版程序中可靠协作，再按模块接真实设备。

| 优先级与建议 | 为什么要做 | 建议落点 | 可以怎样验收 |
| --- | --- | --- | --- |
| 当前先完成478批次整合 | 本批45次累计已过，但还不能证明新增统一退出、真实主入口字典保存等全链正确；旧447结论不覆盖新代码 | `shell/main.cpp`、各主壳接线、报告字典、告警宿主与独立全链用例 | 医院字典到报告保存重查、退出确认、取消阻止退出和告警恢复；对应Windows/ARM构建、依赖及匹配恢复输入；如改正式源，再按影响补回归 |
| 继续定位旧偶发失败 | 通信恢复、旧报告查询、校准引用崩溃和登录几何的历史直接原因尚未全部确定 | `protocol/`及对应页面、原失败输入和诊断工具 | 能受控复现或给出最短因果证据；修复后同条件回归；不靠放宽超时或改掉原失败记录放行 |
| 固定项目到结果的字段合同 | 现有报告夹具不能证明真实项目、任务和结果之间可以正确衔接 | 项目、样本、结果计算及`history/`之间的稳定ID、单位、倍率、精度与异常标志 | 同一匿名任务贯通配置到报告；项目改名或修改单位后，旧报告仍保留检测当时的含义；随后用真实数据对照 |
| 明确任务和协议边界后接真实检测 | 当前样本任务只是本地预设，开始暂停恢复未形成真实闭环 | `samples/`、`protocol/`与未来调度边界 | 给定一条任务，能查到下发消息、应答、执行状态、原始结果和任务ID；断线、重复、急诊和失败恢复有明确规则 |
| 取得可在ARM运行的完整算法材料 | 原DLL无法直接在RK加载；现有两个研究方法覆盖范围有限 | 原AL4A函数清单、`coagulation/`与结果计算接口 | 确认版本、符号、单位和全部实际调用；真实曲线及认可金样本逐项对照，错误不返回假成功 |
| 补校准和质控的实际规则 | 目前保存的是原始点和元数据，尚未证明结果能按正确方法生成和判断 | `calibration/`、`quality_control/`、项目单位与算法接口 | 方法、拟合、反算、审核应用、失控规则含义确定；真实记录和单位可追溯，异常输入有拒绝依据 |

真机连接需要确认SN100型号、协议版本、地址或串口参数、真实曲线和业务方法。条件具备后，先做一个可追踪的最小检测流程，再扩展到全部操作；仪器动作仍按既有模块卡逐项验证。

### 在生产使用前补齐数据与运行保障

| 建议 | 当前依据和影响 | 具体更改方向与验收重点 |
| --- | --- | --- |
| 改进密码存储并明确权限矩阵 | `AccountStore`仍按原`pwd`字段直接存储和比较；部分质控元数据沿原入口没有统一角色门槛 | 设计有版本的密码迁移、带盐派生及旧账户过渡；逐操作列出谁可读写、何时可写。明确兼容行为后实施，不借迁移随意改变角色 |
| 建立成套数据恢复与迁移流程 | 质控和校准库绑定UUID、规范路径及catalog登记；分别提交存在中间状态 | 停写后恢复匹配数据；设计跨目录、跨平台迁移和中断对账。实际演练保存、恢复、重开、隐藏历史与引用保护，应用包校验不能代替数据恢复 |
| 补数据库与文件异常验证 | 已有事务和部分错误恢复；真实磁盘满、异常掉电及长期存储还未等同通过 | 按受影响库和文件设置可恢复实验，核对提交前后数据、部分导出、重启和用户提示；不默认调整所有库的持久化策略 |
| 把运行日志收口为可维护接口 | 各专项已有收发与退出证据，完整统一日志和崩溃能力仍需对照 | 统一时间、模块、请求ID、任务ID和错误；限定容量、轮转及脱敏；繁忙时保留必要原始数据和告警，不能静默丢失 |

`Store`可以先理解为“负责保存和读取这类资料的对象”；`worker`是执行工作的对象，它放在另一个线程中，目的是避免数据库操作占住界面。跨线程传递的是请求和结果数据，界面控件仍在主线程中操作。

```mermaid
flowchart LR
    A[使用者点击保存] --> B[页面读取输入并检查草稿]
    B --> C[排队发送请求]
    C --> D[工作线程中的Store]
    D --> E[权限校验和数据库事务]
    E --> F[提交结果和值快照]
    F --> G[页面更新或保留草稿并显示错误]
```

这张图对应已实现本地保存的主要方式。仪器命令是另一条链路，不能把保存请求直接理解成设备命令。

### 第一条阅读路线 保存医院名称

1. 打开[医院页面](../../06_programs/sn100_host/ui/frmhospinfosetting.cpp)，从`on_btnSave_clicked()`看它怎样收集医院名和当前字典行。
2. 找`requestSave`信号及构造函数中的`Qt::QueuedConnection`连接，确认保存请求交给谁。
3. 打开[HospitalStore](../../06_programs/sn100_host/data/hospital_store.cpp)，从`save()`读校验、事务和真实错误，再看`initialize()`中的数据库连接与持久化设置。
4. 回到页面的`saved`和`error`处理，确认什么时候清草稿、什么时候保留输入。
5. 最后看[shell/main.cpp](../../06_programs/sn100_host/shell/main.cpp)怎样把这个Store放进数据库线程，怎样启动和关闭。

读完这条路线，应能回答：输入在哪里、规则在哪里、文件写到哪里、成功如何确认、失败怎样恢复、退出时谁负责收尾。

### 第二条阅读路线 样本复测只生成草稿

从[SamplePage](../../06_programs/sn100_host/samples/sample_page.cpp)的`resetTasks()`进入[sample_task_reset.cpp](../../06_programs/sn100_host/samples/sample_task_reset.cpp)的`prepareSampleTaskReset()`，看哪些状态允许复位、哪些任务整批拒绝，再回页面看草稿提示和明确保存。这能帮助区分“界面上已选择”“本地已提交”“仪器已执行”三个状态。

### 第三条阅读路线 报告导出

从[HistoryPage](../../06_programs/sn100_host/history/history_page.cpp)的`printReport()`，跟到[history_shell.cpp](../../06_programs/sn100_host/shell/history_shell.cpp)和[report_controller.cpp](../../06_programs/sn100_host/history/report_controller.cpp)，再看报告快照、PDF辅助进程与渲染入口。重点看导出开始后页面能否切走、用户取消时产生什么文件、子进程失败时怎样回报。

学习顺序建议为：医院保存 → 账户权限 → 项目与样本 → 报告 → 线程与关闭 → 通信 → 校准质控和算法。每次先追一条成功路径，再追一条失败或取消路径，比同时展开全部类更容易理解。
