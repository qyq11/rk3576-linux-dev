# 直接运行主程序时的单实例登记候选（2026-11-02）

本候选让使用者绕过启动脚本、直接运行可执行文件时，也按原`isAppOpenMultiple`开关判断是否继续启动。只在`temp`准备一个主程序插入补丁，未改正式main、构建、配置或计划；没有启动产品、访问网络、连接板卡、操作界面或创建实际运行锁。

## 原Windows实际行为

原`06_programs/sn100_host_reference/Seerain450_PC/main.cpp:43`的`checkOnly`使用固定名称`fortest_abc123`，调用`CreateMutex(NULL,FALSE,L"fortest_abc123")`。它不是等待临界区：初始所有权为FALSE，之后没有等待或释放互斥量的调用，实际依据是同名对象是否已经存在。

原调用顺序为第226行创建`QApplication`，第228行`getConfig_debug()`，第230行调用`checkOnly()==false && !SystemCommon::isAppOpenMultiple`。`getConfig_debug`从当前工作目录的`config_Debug.ini`读取`userOption/isAppOpenMultiple`，默认false；`public/systemcommon.cpp:77`的全局初值也是false。

| 原场景 | 实际行为 |
| --- | --- |
| 首次登记，不论开关真假 | 新建同名对象，保留未关闭的句柄直到进程退出，继续启动 |
| 已有登记，当前配置禁止多开 | 关闭本次打开的句柄，提示“错误 / 程序已经在运行!”，返回0，不进入后续业务启动 |
| 已有登记，当前配置允许多开 | 仍先调用checkOnly并打开同名对象，然后关闭自己的句柄，继续启动；并不跳过检查 |
| 最初持有句柄的实例退出，其他允许多开的实例仍在 | 后来的实例没有继续持有登记；原对象可能消失，新的禁止多开实例可能再次启动。这是原边界，不能偷偷改成所有多开实例都继续登记 |
| 创建句柄为NULL或其他错误 | 原函数只认`ERROR_ALREADY_EXISTS`，其他错误都返回true，存在错误放行；没有单独区分权限、环境或同名其他对象类型错误 |

固定名称不含程序目录、工作目录、配置路径或用户名。同一普通Windows登录/Terminal Services会话里的不同目录和配置会遇到同一名称。无`Global\\`前缀，不能称整机全局；默认按Windows会话命名空间处理，也不是按Win32 Desktop对象分别隔离。跨用户同会话还受默认安全描述符影响，原源码没有保证其成功共享。本轮只读源码，没有运行Windows验证这些系统行为。

## 当前配置消费者与插入位置

当前`RuntimeSettings::debug.allowMultipleInstances`已默认false；`original_runtime_settings.cpp`从同一原键读取，但正式main此前没有消费它。候选直接使用这个字段，不新增配置、不改键名/默认值，也不按操作系统选择另一套开关。

正式main现有顺序是创建`QApplication`、解析显式参数、从`--original-db-root`读取汇总运行配置。候选在该现有读取成功之后、`OriginalRuntime::SystemProfile`及所有业务线程和设备连接创建之前登记。汇总读取比原`getConfig_debug`多做只读配置检查，本片不为提前几行登记而另加一套隐式当前目录配置读取。

没有指定原资料根的旧独立入口继续使用现有`RuntimeSettings`结构默认false，不突然从当前目录读取另一个INI。正常RK原资料启动路径使用显式原根。本片不改启动脚本的生命周期锁；脚本本身已有额外互斥，不能用脚本启动验证代替直接可执行入口。

登记对象的空构造放在`QApplication`之前，实际登记仍在配置读取后。这样不提前取锁，又能让登记对象晚于`QApplication`析构，覆盖业务和Qt平台退出清理。这是独立复核发现并修正的初版退出顺序遗漏。

## Linux适配范围和有意差异

当前候选的Linux作用域明确为：**同一有效用户编号（UID）、共享同一/tmp文件系统命名空间的进程**。正常`lckfb`启动使用`geteuid()`，不硬编码其数值。固定路径为：

```text
/tmp/sn100-single-instance-<有效UID>/fortest_abc123.lock
```

目录要求同一用户所有、权限0700（只有该用户可访问），文件要求普通文件、同一用户所有、单一硬链接、权限0600（只有该用户可读写）。拒绝符号链接，不改已有所有者或权限。锁文件打开时不截断，也不写入或读取内容；成功后只保留一个文件描述符。`flock(LOCK_EX|LOCK_NB)`只尝试一次非阻塞独占登记，退出只关闭自己的描述符，从不删除文件、不猜PID、不杀进程、不清他人锁。程序异常结束后由内核释放文件锁，后续可直接登记同一个未锁文件，不靠删所谓“陈旧锁”恢复。

`CLOEXEC`让报告辅助进程等通过exec启动的子程序不继承持锁。路径不依赖可执行文件目录、原配置根或每次启动变化的`XDG_RUNTIME_DIR`；已有`rk_board.sh`会为每次运行设置不同运行目录，因此不能直接把那个目录当全应用登记名。

以下差异必须保留在验收说明，不能用“Linux等价实现”一句带过：

- 同一Linux用户跨不同图形会话仍互斥，比原Windows按登录会话隔离更严格；不同Linux用户互不登记，不能宣称整板所有用户只有一个SN100。
- 不同容器或隔离的/tmp命名空间不共享此登记。当前RK启动脚本没有声明`PrivateTmp`，但本轮没有上板核实际服务环境，不能把源码推断当实测。
- 文件锁不能阻止同一用户的外部操作者或清理器删除/替换目录及文件。候选会在取得锁后复核当前名称仍指向同一个文件，但不能保证其之后永远不被外部移走。正常运行条件包括不由外部清理这些登记路径；若以后要求抵御外部删锁或精确隔离多图形会话，需另定Linux登记作用域，不能悄悄放宽或改成另一业务开关。
- `QApplication`及Qt平台初始化仍先于实际登记，与原调用顺序一致。EGLFS第二实例可能先在Qt平台/显示资源初始化阶段失败，是否能到达友好“程序已运行”提示须RK实测；本片没有把它说成已保证。
- 只有带本登记代码的主程序参与检查；旧Linux版本没有该登记，不会自动被新程序识别。换版前仍须按现有流程正常退出旧版，不能用本候选宣称已排除未知旧进程。

Windows分支使用显式`CreateMutexW`和原固定名称，继续按系统默认会话登记；本轮不进行Windows构建或运行。其他尚未接入的平台明确报环境错误，不假称已有实例或正常首次启动。

## 已有实例与环境错误分开处理

只有文件锁争用的`EWOULDBLOCK/EAGAIN`或Windows的`ERROR_ALREADY_EXISTS`才归为“已有登记”。当前配置禁止多开时保留原提示和返回0；允许多开时关闭本次打开的描述符/句柄后继续，不持续占用最初实例的登记。首次成功登记即使配置允许多开也仍持有登记，保留原先检查再判断开关的顺序。

目录/文件权限、所有者、类型、硬链接、名称变化、系统调用失败或不支持的环境均单独报`SINGLE_INSTANCE_ENVIRONMENT_ERROR`，显示实际原因并返回2；既不称“已有进程”，也不放行业务初始化。**错误时停止是相对原创建失败误放行的有意安全差异**，包括当前配置允许多开时也不把登记环境坏了当作一次正常检查。没有接管、修权限或自动清理操作。
