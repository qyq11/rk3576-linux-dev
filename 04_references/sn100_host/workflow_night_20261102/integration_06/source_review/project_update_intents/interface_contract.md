# 明确保存后的单项目同步：实施接口小结

本切片基于重连v2固定累计片99dd8eda，另写本目录，不改686f、v2或正式4e。先接已存在的校准小窗 `last_cal_para` 保存；普通项目保存和210dd7de原组分开关只给同形接口，由总窗口串行接真实生产点。新增/删除项目清单不是本片单项目更新能力。

只读合同已核：`CAL_sync_review/contract.md` SHA-256 f7990d97323c9ec3530336dfae94206370e6f779175a6883dda6cc39b445538c；`save_intent_contract.md` SHA-256 3cb5bb0a3275028adfd3ce39a2ce52acd73f8d442554d607208b9a78906feff8。原Up实际包含last_cal_para；UP回写/普通reload不能产生本地保存意图，不能删canStart的全文件版本校验。

## 生产结果与通知

新增按值通知 `OriginalProjectSaveNotice`，字段为来源、源保存请求号、原数据根、原文件名、该提交版本中的项目编号与名称、写前SHA、实际写后SHA、`commitSeen`、`verifiedSnapshot`及说明。`root + originalFileName`定位文件；id/xuhao只断言这个提交版本，回读后按同一文件接受原允许的新xuhao。

`OriginalSampleRepository::saveCalibrationParameters` 增加提交结果输出，入口清空；写前复制文件名及身份，commit成功立即记录commitSeen；仍持原写锁回读提交后快照，按原文件名定位并验证实际新SHA后才标verifiedSnapshot。refreshProjects失败不把已经提交说成回滚，也不再用已失效的容器指针取身份。

`SampleStore`在SQL所属线程、原项目写锁内排出生产通知（intent=0），然后才释放写锁；回调只发值信号，不做SQL重入。Root立即撤旧ready，并按相同路径把所有生产通知依次排给同一消费者。消费者回执intent>0只关联同一次保存，不能覆盖Root已见的新保存。普通项目/组开关也必须在同一写锁内排通知，不能有一条直达同步器、另一条绕GUI而倒序。登记前原canStart全文件hash仍保护实际写入变化。提交但未核实新快照只建立阻断，不发Up或猜hash。写前失败不建意图。

## 同一个消费者

通知和阶段是明确值对象，声明/注册Qt元类型；跨线程槽名、Q_ARG类型名和moc一起核。未来普通项目/组开关也把通知交给 `SampleStore::enqueueOriginalProjectUpdate`，由同一同步器分配递增本地意图号，不把请求号写进原协议。

`OriginalDeviceSync`增加独立单项目等待通道：同连接只一份在途冻结参数，按原文件名每项目最多一份最新未发送意图，保留其他项目已确认指纹。Root仅在当前真实状态及原配置发送守卫允许时唤醒已存在的队列，不凭Qj或reload新建/重试已拒绝意图。单项目批次走独立发送回执，不能复用“发送失败即invalidateOriginalDeviceSync”的旧入口，以免碰检测在途事实。

正常已完成初始同步的LinuxNew路径：精确重读通知文件/版本/编号/名称 → 冻结完整原Up参数 → 原Up与UP查询有序进入当前连接 → 10秒内匹配同项目全部已发送字段 → 在原写锁/事务内再核文件身份和版本并回写 → 重读同文件、更新实际编号和确认SHA → 结清该意图。只有初始同步完成、没有待确认/未知项目且原全文件校验通过，才恢复ready。

Root记录每文件最新通知和阶段，旧ready=true、旧意图或旧连接回执不能覆盖新保存。纯项目重读、UP回写和曲线保存只刷新，不生成保存通知。当前last_cal_para的值和Up编码/顺序/精度不改，不涉及计算或拟合。

## 有界并发与停止边界

- 同文件未发送的连续明确保存可用最新版本取代旧版本，发“被新保存取代”回执；普通queued与active not-sent两条替换分支都核旧afterSHA等于新beforeSHA，保留从已确认基线到最新提交的版本链断言。已可能发送的冻结参数不能替换。Prepared尚无实际入队结论时，等真实发送回执；确认未attempt可取代，可能已发送才转未知。
- 在途后同文件发生另一实际版本提交，保留新本地值和最新未发送意图，旧在途标结果待核；旧UP不能覆盖新值。不同项目的意图串行等待。
- 初始同步未结束或设备/任务仍忙，意图仅排队。既有初始等待快照不被新保存替换；若新保存导致该冻结快照冲突，明确保留已提交/待核状态，不假装初始同步成功。完整任务旧协议不发新协议Up。
- 尚未尝试即守卫拒绝：保留“未发送”；Up可能已入队后失败、超时、不同参数或冲突：保留“结果待核”。都不借下一条Qj盲重试，不撤销本地提交。
- 断线/换代停止旧传输等待，保留本地提交和未确认记录，不自动转发旧意图。新连接仍由重连v2先核在途，再按原初始同步读取当前磁盘资料；只有实际确认的文件版本可结清此前待确认事实。
- 当前已读项目清单决定每文件队列上限；不支持的清单增删、资料不可核及跨进程恢复须明确阻断/列范围，不能丢弃后报告ready。本片不新增跨进程对账台账，不清任务占用、报告号、TD/Tr/TR集合或试剂未知保护。
- CAL提交前按冻结的原文件名检查已读清单和预算；Repo刷新后、打开写库前还核实际目标仍是这个文件，不能用相同id/SHA的改名文件绕过预检。无法容纳时先拒绝提交，保留草稿。
- UP实际改xuhao时仍保存同文件真实编号/确认SHA；另留“预设引用待核”，只阻断开始，不按旧id改写架/任务，不混入Us未知，不由新连接或普通ready清除。当前没有解除入口，等待后续有原版依据的引用迁移。

本小结是实施边界，不是已经实现或功能通过。后续只做必要ARM64局部对象编译；不运行产品、真实DB、网络、RK、模拟或UI。
