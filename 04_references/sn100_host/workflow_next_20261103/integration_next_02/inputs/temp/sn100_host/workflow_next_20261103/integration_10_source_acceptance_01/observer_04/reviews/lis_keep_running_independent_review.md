## 需要收口的项

**P2：解析器接受过短的已就绪观察时长。** `candidate/review_lis_observation.py:139–140` 只将 `duration_ms`、`startup_wait_ms` 核为非负整数。后续软件评估条件（第237–265行）和返回成功的条件（第337–338行）没有在 `startup_ready=true` 时核 `duration_ms >= 15000`。因此，只读控制流可确定：其他内容合法时，声明已就绪而 `duration_ms=0` 的快照仍可以得到软件 pass 与工具退出0。这是对现有条件的静态推导，未构造或运行假数据。

建议在解析器中加入这条独立时长约束，并保持 `startup_ready=false` 时必须 `duration_ms=0` 的现有约束。C++的正常完成路径确实只在 `observing_.elapsed() >= 15000` 时调用 `finish(true)`（`lis_keep_running_review.cpp:111–114`），不足15秒的已就绪快照不应被解析器接受。60秒就绪截止已在C++第117行、读取页面之前判断；实际耗时可能包含事件循环延迟，不宜把“超过计划毫秒数”本身当成业务关闭或伪造证据。若解析器还要核就绪截止，应明确判定时刻与实际耗时记录的区别。
